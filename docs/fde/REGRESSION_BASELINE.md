## Root cause of the one failing test (confirmed, not hypothesized)

`tests/test_rag_config.py::TestPreviewRagConfigEndpoint::test_adversarial_rate_limited_second_call` (and two sibling tests in the same class) called the real `preview_rag_config_endpoint`, which unconditionally calls `_audit_admin_action()` → `repositories.append_audit_log()` at the end of every successful request. That function was **not mocked** in these three tests — the only tests in `test_rag_config.py` with that gap (confirmed by reading every test in the class). In this environment, `AZURE_KEY_VAULT_URL` is configured but Key Vault authentication is currently failing (an expired Azure CLI Temporary Access Pass — the same recurring sandbox-credential friction documented repeatedly elsewhere in this engagement's history), so the real `get_container()` call inside `append_audit_log()` walks `DefaultAzureCredential`'s full chain to failure for `COSMOS_ENDPOINT` and `COSMOS_KEY` — roughly 6 real seconds each, ~12s total — before `_audit_admin_action()`'s own try/except swallows the exception.

That ~12s of real wall-clock time, elapsing *inside* the first of the test's two back-to-back calls, pushed the gap between them past the rate limiter's 5-second window (`_RAG_PREVIEW_MIN_INTERVAL_SECONDS` in `azure-functions/api_blueprint.py`), so the second call was never rate-limited. Confirmed deterministic: failed 5/5 isolated reruns before the fix, passed 3/3 isolated reruns after it (0.15–0.16s each).

**Fix:** added `monkeypatch.setattr(repositories, "append_audit_log", lambda entry: entry)` to the three affected tests, matching this file's own stated convention ("repositories.* is monkeypatched per test so these never touch a network"). Also added `TestRateLimitedHelper` (3 new tests) to cover `_rate_limited()`'s own logic directly, independent of any endpoint's I/O, using a fake clock — so a future regression in the limiter itself (as opposed to a test-isolation gap) would be caught without depending on real timing.

**Not done:** the rate-limit assertion itself was never weakened or removed, per instruction. The underlying Key-Vault-credential slowness itself is an environment condition (expired sandbox TAP), not a code defect, and is unrelated to this engagement's own code — not something this loop fixes.

## Known pre-existing environment friction (not a defect in this codebase)

The Microsoft Learn sandbox's Azure CLI Temporary Access Pass expires frequently and makes any code path that calls `secrets_loader.get_secret()` for a Key-Vault-backed secret slow (several seconds per secret) whenever it has expired. This has been observed and documented repeatedly throughout this engagement. It explains both the one test failure above and the general slowness of `test_rag_config.py`'s full module run (61 tests, 98.98s — several other tests in that file also don't mock Cosmos/secrets access and are consequently slow, though none of them are currently timing-sensitive enough to fail outright). Flagged here for awareness; not in scope to fix broadly in this loop unless it starts causing further test failures.
