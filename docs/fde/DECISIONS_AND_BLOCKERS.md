# Decisions and Blockers

Carried forward from the Phase 1 roadmap/contract (see the Claude Docs artifact, Section 10), plus any new ones surfaced by this loop.

## Open, not yet blocking current work

1. **Fairness measurement scope (F-16/F-04).** Should demographic-group fairness measurement ever collect/infer sensitive candidate attributes, or stay strictly limited to the static "no protected-attribute field reaches scoring" guard already built (Task 7)? Blocks F-16 going beyond its minimal slice and blocks F-04 (interviewer-candidate matching) entirely, per the roadmap's dependency graph. No safe default exists without this decision — proceeding without it would risk exactly the undocumented-lawful-basis problem the original audit flagged. **Requires user approval before F-04 is eligible.**
2. **Regulatory scope for F-13.** Generic framework demo vs. a specific, named jurisdiction. Legal-interpretation task, not primarily code. **Blocks F-13 entirely until answered; safe default: omit from the build plan** (already the roadmap's recommendation).
3. **Local-model infrastructure budget for F-25.** Is any GPU/self-hosted model infrastructure actually in scope? **Safe default: frontier-only comparison framework, local arm explicitly marked unavailable** — doesn't block starting a framework-design slice if ever prioritized, just blocks claiming real local-model numbers.
4. **F-20's real target call site.** The roadmap's own suggested idempotency target ("duplicate-email prevention") has no real call site yet, since F-05 (email sending) isn't built. Either F-05 must land first, or a different existing consequential action needs to be chosen as F-20's minimal-slice target. **Not currently blocking** — F-20 is simply not eligible yet without one of those two resolutions; flagged here rather than silently skipped.
5. **F-19's unanswerable-question score ceiling is not reliably calibrated (real finding, not a bug).** A live run of `rag_evaluation.run_retrieval_evaluation()` against the real semantic index measured the one genuine non-match golden question (RAGEVAL-004) at top retrieval score 0.483 — above the `_NO_MATCH_SCORE_CEILING = 0.35` set from an older chunking system's historical numbers — while a genuine match (RAGEVAL-003) scored only 0.337, lower than the non-match case. Real match and non-match score ranges measurably overlap in this embedding space (observed: matches 0.337–0.777, the one non-match 0.483). A single fixed top-score ceiling is therefore NOT currently a reliable standalone "no good match" signal here. **Not fixed by moving the number** (would be fitting a threshold to one data point and hiding a real finding, which this engagement explicitly treats as prohibited — see the rate-limiter test precedent above). **Safe default taken: left the ceiling at its originally-documented value; the live evaluation honestly reports 3/4 (0.75) hit rate with this one case failing, not a forced 4/4.** Resolving this properly needs more real golden "unanswerable" questions to actually calibrate a threshold (or a different detection approach, e.g. a relative/comparative score check rather than an absolute one) — out of scope for this minimal slice. Flagged for whoever extends F-19 next, not silently absorbed into a passing number.
6. **One persona vs. both for F-08's frontend chat UI (Task 5, still not built).** Recommended in the Phase 1 contract: scope to one persona first (candidate-facing was originally suggested, but this app has no candidate-auth persona — see note below). **Not blocking current loop** since F-19/F-21 are the active tasks; revisit when F-08's UI half is picked up.
7. **Chat-data retention policy for any future F-08 persisted transcripts.** Currently N/A — F-08's endpoint is stateless (no persistence), so this doesn't block anything yet. Will become live the moment anyone proposes persisting chat history.
8. **RESOLVED — real Azure was unreachable from this environment; root cause was a local VM clock skew, not an expired Azure session.** Initially misdiagnosed as an expired Temporary Access Pass (the pattern this engagement has repeatedly attributed slowness/failures to). The user re-ran `az login --use-device-code` and signed in successfully, but the local Azure Functions host STILL failed to start with the identical "Request date header too old" error against Azure Storage — proving it wasn't an AAD/TAP problem. Direct verification (`date -u` vs. an external time source's real `Date` header) confirmed the actual root cause: **this VM's system clock was running ~5 hours 30 minutes behind real time.** Azure's Shared-Key Storage authentication (used by the Functions host's own `AzureWebJobsStorage` connection) rejects any request whose client-generated timestamp drifts more than ~15 minutes from the server's real clock — independent of any Azure AD session validity. This also plausibly explains much of this whole engagement's chronic "token expired" friction (a skewed local clock makes AAD token expiry checks behave inconsistently too), not just today's isolated incident.
   - Attempted self-fix: `w32tm /resync /force` — failed, "Access is denied" (this account is not a local administrator).
   - **Fixed by the user directly** (outside this session's own privileges) — confirmed via `date -u` matching a real external time source exactly afterward.
   - **Verified resolved, end to end, for real:** Functions host started cleanly (no auth error); real login, real F-21 structured-output-gate call, and real F-21 match-quality judge call all succeeded against the live backend. See IMPLEMENTATION_STATUS.md's F-21 entry for the actual live results, including a genuine data-quality defect the gate caught (`Resume Strength Score` stored as a string, not a number, in the real candidate record).

## Resolved / not a blocker (recorded for traceability)

- **"Does F-08 need a candidate-authentication persona?"** — No. Confirmed via real inspection: this app has no authenticated candidate login path (only an anonymous email-lookup endpoint with its own documented gap). Building candidate auth to make F-08's demo "cleaner" would be introducing new authentication infrastructure/roles without an approved requirement — explicitly prohibited by this loop's own safety boundaries. F-08 stays staff-facing, reusing the existing `candidates.read`/`interviews.manage` permission model. This is a closed decision, not an open one — recorded here so it isn't re-litigated.
- **"Is the F-19 golden dataset allowed to use real candidate names/contact details?"** — No. Per explicit instruction: any golden-dataset content derived from `semantic-library/index/resume-chunks.json` must be sanitized before being committed to a fixture/dataset file — no real names, emails, phone numbers, or other identifying details. Resolved by design: F-19's golden dataset will reference REAL, GENERIC skill/technology terms actually present in the real index (verified via grep), not real candidate identities, and will not copy raw chunk text into committed files.
